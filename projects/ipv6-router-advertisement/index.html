Project case study / IPv6 Router Advertisement

Processing IPv6 Router Advertisements in Rust

A Linux library that receives Router Advertisements, tracks lifetimes and emits complete state changes for each network interface.

The problem

Custom network management needs more than a received packet. Which DNS servers and prefixes are still valid? What happens when several routers advertise information, or when their lifetimes expire? Protocol data needs to be combined into consistent state over time.

My contribution

I develop this Rust library as a building block for network managers and embedded systems. It processes Router Advertisements on Linux and exposes changes through an asynchronous event stream. The application above it decides what to do with that information.

The architecture decision

Reception, parsing, lifetimes and aggregation are separate layers. Changes emit complete state rather than individual packet fragments that callers need to assemble. The library does not configure addresses or routes, or start a DHCPv6 client. Configuration policy stays with the application.

What you can inspect

The README describes DNS options (RDNSS/DNSSL), prefix information, router flags and expiry events. The testing strategy covers unit tests, integration tests with mock ICMPv6 sockets and replaying captured Router Advertisements. Code, examples and tests are public.

How this connects to team development

The same concerns appear in Linux services: asynchronous processing, explicit state boundaries, time dependencies and tests for edge cases. These are decisions we can discuss in the context of your project during Embedded Linux training.
